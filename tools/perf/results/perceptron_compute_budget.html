Why a parked robot uses 4.2 cores

Almost all of it is wake-ups. Every message delivered to a node wakes a DDS thread and an executor; at these rates that per-message overhead, not any algorithm, is the bill. map_server — which does nothing after sending the map — costs 12% of a thread purely from receiving other nodes’ bond heartbeats.

What each switch does

Hollow dot = idle and localised, filled = navigating. Grey band = run-to-run noise (±0.47 cores). Every change was run once and compared with a baseline interpolated from the runs either side of it, because this laptop drifted by up to 20% over an hour as it heated up. On this laptop the price of a unit of work also depends on how busy the machine is (turbo clock, hyper-threading, WSL2 scheduling): in the behaviour-neutral bundle, nodes doing exactly the same work as before — map_server, the lifecycle managers, battery_node, AMCL — cost 24–32% less, and a fixed benchmark running alongside sped up by the same amount. So every saving below includes the remaining nodes getting faster cores; the Jetson Nano section measures the edge directly.

What to change

1 · Turn RViz off on the robot computerno behaviour change

RViz alone is 67% of a core and 235 MB; switching it off measured -1.69 idle / -2.33 navigating cores on the laptop. On the edge device run it on the laptop instead, and keep costmap displays off — each subscribed costmap makes the robot serialise it over Wi-Fi.

ros2 launch perceptron_robot_bringup nav.launch.py jetson:=192.168.1.7 \
    map:=$HOME/perceptron_test_ws/src/perceptron_navigation/maps/room_map.yaml \
    ekf:=false overlay:=false rviz:=false aruco:=false

2 · Stop the ArUco localizer once it is not neededno behaviour change

nav.launch.py never exposes it, so your command always starts it — yet with --no-aruco on the Jetson it receives nothing, while its Python TF listener and 92 Hz /odom subscription cost 59% of a core and 123 MB. Passing aruco:=false on the nav.launch.py command line already reaches localization.launch.py. Measured: -0.70 idle / -0.68 navigating cores on the laptop.

3 · Turn Nav2 lifecycle bonds off (or slow them)trade-off

Nine bonds heartbeat at 10 Hz on one shared /bond topic that every bond subscriber receives (102 Hz × 11 subscribers). The two lifecycle managers alone cost 37% of a core and every Nav2 server pays ~5–10% for it. Measured with the Nav2 manager’s 7 bonds off: -1.26 idle / -1.08 navigating cores on the laptop; on the Nano, the optimised run (all 9 bonds off, together with the lean bridge) took each idle server from 7–17% to 0–2%. Trade-off: the lifecycle manager no longer notices a crashed server — use respawn instead. Set bond_timeout: 0.0 in both lifecycle managers’ parameter dicts (not with a global SetParameter — see the method notes).

# localization.launch.py -> lifecycle_manager_localization parameters
{'use_sim_time': False, 'autostart': True, 'node_names': ['map_server', 'amcl'], 'bond_timeout': 0.0}

4 · Make jetson_bridge_node publish at the rates consumers needcode change

It republishes every STM32 frame: odom, TF, IMU and two battery floats at ~100 Hz each, and wakes for ~195 Hz of raw “reply” frames it throws away. Own cost 58%, plus battery_node 31% and every TF listener downstream. A 4-change patch (subscribe only to the ZMQ topics it uses, battery at 2 Hz, skip IMU work with no subscriber, odom+TF at ≤50 Hz while integrating every sample) measured -1.01 idle / -0.89 navigating cores on the laptop. On the Jetson side, stop forwarding the raw 0x55/0x56 frames as “reply”, which also frees Nano CPU.

5 · Controller: publish less debug, then decide on the ratetrade-off

DWB records the full evaluation of all 800 trajectories every cycle whenever publish_evaluation or publish_trajectories is true (both default true), even with no subscriber. Measured on controller_server itself while navigating: debug publishers off -20%, 10×20 samples -46%, 10 Hz -34%, all three -51%. On the laptop total these sit inside run-to-run noise because the controller is only part of the bill; on the Nano they matter. controller_server is 71% of a core while navigating on the laptop and 68% of a Nano core (it cannot hold 20 Hz there). At 0.35 m/s, 10 Hz is 3.5 cm per cycle. Unload MPPI first: while FollowPathMPPI is loaded, any controller_frequency below 20 Hz makes it refuse to configure (“Controller period more then model dt”, model_dt 0.05 s) and the entire Nav2 bringup aborts — measured twice before this was traced.

FollowPath:
  publish_evaluation: false
  publish_trajectories: false
  publish_global_plan: false
  publish_transformed_plan: false
  debug_trajectory_details: false
controller_frequency: 10.0   # edge only; vx_samples 10, vtheta_samples 20

6 · Size the global costmap to the room and unload unused pluginsno behaviour change

The 48 m rolling window is 921,600 cells for a 12 × 11 m map (52,779 cells) and is sent in full. Yet it is not where the CPU goes: sizing it to the map changed planner_server by -5%, and every costmap change stayed inside the laptop noise. Do not coarsen it to 0.10 m: that run could not plan through the 0.75 m doorway (8.9 Hz controller, planner failures). Unloading MPPI, three spare planners and two behaviours: -0.10 idle / -0.06 navigating cores on the laptop — not a CPU win on its own, but on a Jetson Nano it is mandatory — the Humble arm64 MPPI plugin kills controller_server with SIGILL on the Cortex-A57 even though your behaviour tree never uses it.

global_costmap: rolling_window: false   # drop width/height; static layer sizes it
always_send_full_costmap: false
controller_plugins: [FollowPath]
planner_plugins: [Smac2D]

7 · EKF on is not a CPU cost hereno behaviour change

ekf:=true measured -0.23 idle / -0.25 navigating cores on the laptop — inside the noise. The filter costs 18% of a core, and in exchange the bridge stops publishing TF at ~100 Hz (-13% on the bridge) while the EKF publishes it at 30 Hz, so every TF listener does less. Choose EKF on accuracy grounds; CPU is not a reason to leave it off.

8 · AMCL and composition are second-ordertrade-off

AMCL at 240 beams × up to 2000 particles is cheap while the robot is parked and only updates on motion; with emulated 5 Hz updates, 60 beams cut AMCL itself by 20% and beams + 200–800 particles by 22% (laptop total: inside noise). Composition (one container) saved memory (-59 MB) but with component_container_isolated it missed more controller deadlines; worth a retest with a multithreaded container before adopting.

Laptop versus Nano, per core

Identical kernels compiled with -O2 on both. Compute runs 3–7× slower per core on the Nano, but a thread wake-up — which this stack performs thousands of times per second even while idle — is 3.9× faster there than inside WSL2. That is why a flat “laptop × 5” would be wrong, and why the Nano was measured directly.

Raspberry Pi 5 (estimate, not measured)

A Cortex-A76 core at 2.4 GHz is typically 2.5–3.5× a Cortex-A57 core at 1.48 GHz on single-thread integer and floating-point work, so dividing the Nano measurements by that range gives 0.78–1.09 cores navigating for your current stack and 0.15–0.21 cores for the optimised one, out of 4. Memory is the same as on the Nano (~354–483 MB). Treat these as planning numbers; the same harness (tools/perf) runs on a Pi 5 with Ubuntu 22.04 and would replace them with measurements.

How this was measured

Load

CPU time from /proc/<pid>/stat for every process in the launch tree over 30 s idle and 25–30 s navigating windows; memory as PSS from smaps_rollup. The robot stayed parked: Nav2 ran for real, but the bridge’s /cmd_vel was remapped so motors never moved. To load DWB as if cruising, controller_server’s odometry was fed the velocity Nav2 itself commanded; AMCL was asked for 5 filter updates per second (request_nomotion_update) to stand in for motion.

Input

The laptop runs replayed the Jetson’s own recorded payloads — odometry, IMU, battery, raw replies at the measured 100 Hz and LiDAR at 10 Hz, with fresh timestamps — so the robot’s battery and Wi-Fi could not change the input between runs. A stretch of the recording where someone walked past the robot was cut after it was found to block the planner; affected runs were repeated.

Noise

The laptop slowed by up to 20% as it heated (confirmed with a fixed benchmark). Every change was bracketed by baselines and compared with the time-interpolated baseline. Back-to-back baselines differ by ±0.24 cores idle and ±0.22 navigating (1 sd, single run); differences inside that are not claimed.

A trap found on the way

A global SetParameter in a launch file adds -p to every node, and any -p makes a node’s YAML beat its inline dict: AMCL silently came up with use_sim_time and set_initial_pose from nav2_params.yaml. The first bond-off runs were discarded for this and re-run with the setting scoped to the Nav2 include. Keep this in mind in your own launch files.
